# 핸드오프 — 포장 규격 자동 인식 (모바일 발주 경로)

작성 2026-09-08 · 웹 구현 완료(미배포) · 모바일 경로 미착수

## 한 줄

회원이 양파 1포를 **"15kg"** 으로 발주하면 시스템이 **"24,000원짜리 15개"** 로 읽어
360,000원을 청구하는 일이 있었습니다. 품목마다 포장 규격을 두고, kg 수량이 규격의
**정확한 배수일 때만** 포장 단위로 되돌리는 기능을 넣었습니다.

웹(`apps/web`)의 발주 화면과 명세서 생성에는 들어갔습니다.
**모바일 발주 경로(`/api/member/orders`)와 앱 화면이 남았습니다.**

---

## 왜 만들었나

2026-09-07 실제 사고입니다.

| | |
|---|---|
| 발주 | 할매솥뚜껑삼겹살 일산킨텍스점, 양파 **15 kg** |
| 시스템 계산 | 15 × 24,000 = **360,000원** |
| 실제 받을 금액 | 1포 = **24,000원** |
| 과다청구 | **336,000원** |

사장님 확인: **양파 1포 = 15kg, 청양고추 1박스 = 10kg** 입니다.
회원은 앱에서 단위를 고르지 않고 그냥 kg 칸에 15를 넣습니다.

## 이미 되어 있는 것 (건드릴 필요 없음)

**DB** — `products` 에 컬럼 두 개가 이미 있습니다 (운영 반영 완료).

| 컬럼 | 뜻 | 현재 값 |
|---|---|---|
| `pack_unit` | 포장 단위 | 양파 `bag`, 청양고추·청양고추B `box` |
| `kg_per_pack` | 포장 하나가 몇 kg | 양파 `15`, 고추 `10` |

마이그레이션: `supabase/migrations/20260908000000_add_product_pack_size.sql`

**변환 규칙** — `apps/web/lib/products/pack-size.ts` 의 `toPackQty()` 하나뿐입니다.
테스트 `pack-size.test.ts` 6개 통과.

```ts
toPackQty(15, 'kg', { pack_unit: 'bag', kg_per_pack: 15 })  // → { qty: 1, unit: 'bag' }
toPackQty(30, 'kg', 양파)   // → { qty: 2, unit: 'bag' }
toPackQty(8,  'kg', 양파)   // → null  (배수가 아니면 손대지 않는다)
toPackQty(1,  'bag', 양파)  // → null  (이미 포장 단위)
```

**규칙은 "배수만"입니다.** 20kg 을 "1포 + 5kg" 로 쪼개지 않습니다. 3kg·8kg 은
정말 낱개로 시킨 것이므로 kg 그대로 둡니다. 사장님이 정한 규칙이니 바꾸지 마세요.

**웹에 이미 적용된 곳**
- `apps/web/app/member/order/OrderForm.tsx` — 수량 칸에서 포커스가 빠질 때 변환,
  "15kg = 1포로 바꿨어요" 안내 표시
- `apps/web/lib/specs/sync.ts` — 명세서를 만들 때 한 번 더 변환(마지막 관문)
- `apps/web/app/admin/products/[id]/ProductEditForm.tsx` — 품목마스터 규격 입력칸

## 할 일

### 1. 발주 API 에 변환 넣기 (핵심)

`apps/web/app/api/member/orders/route.ts`

모바일 앱은 DB 에 직접 쓰지 않고 이 라우트를 부릅니다
(`apps/mobile/app/(tabs)/order.tsx` 의 `submitOrder`). 그런데 앱은 단위를 고르는 UI 가
없어서 **항상 `product.default_unit`**(양파는 kg)로 보냅니다. 그래서 앱 발주는
지금도 15kg 로 저장되고, **발주 문자에도 "양파 15kg" 로 나갑니다.**

라우트 120행 근처에 이미 "마스터 강제 검증" 블록이 있습니다. 거기서 `products` 를
조회하고 있으니 `pack_unit, kg_per_pack` 을 같이 select 해서, 허용 단위 검증 **뒤에**
`toPackQty()` 를 걸면 됩니다.

명세서 쪽(`sync.ts`)은 이미 막혀 있어 **청구 금액은 지금도 맞습니다.**
이 작업으로 고쳐지는 것은 **발주 문자와 매입 집계**입니다.

### 2. 같이 고쳐야 하는 버그 — 단가 보정이 단위를 안 본다

같은 파일 149~190행. 클라이언트가 단가를 못 채워 보냈을 때의 안전망인데,
`price_snapshots` 에서 **단위를 안 보고 최신 한 줄**을 집습니다.

```ts
// 지금 (틀림)
.select('supplier_product_id, sale_price, effective_from')
.lte('effective_from', businessDate)
.order('effective_from', { ascending: false })
```

변환으로 단위가 kg → bag 로 바뀌면 단가도 그 단위 값으로 다시 잡아야 하는데,
이대로면 kg 단가(3,000)가 1포에 붙어 **1포 3,000원**이 됩니다.

**이 실수는 이 프로젝트에서 네 번째입니다.** 명세서 생성 · 매입원가 · 단가 전파에서
같은 원인으로 터졌습니다. 규칙은 하나입니다 —

> 단위가 다른 단가는 그 단위의 가격이 아니다. 단위가 둘 이상인 품목은
> 그 단위 단가가 없으면 **다른 단위로 때우지 않는다.**

정답 구현이 `apps/web/lib/specs/sync.ts` 의 `buildPriceMapByProduct()` 에 있습니다.
가능하면 그 함수를 그대로 부르세요. 새로 짜지 마세요.

### 3. 모바일 앱 화면

`apps/mobile/app/(tabs)/order.tsx`

- 서버가 단위를 바꿔 저장하므로, 발주 후 내역에 **"1포"** 로 보입니다.
  회원이 15를 넣었는데 1포로 보이면 놀랄 수 있으니, 웹처럼 안내를 붙여 주세요.
- 웹과 같은 경험을 원하면 수량 입력을 마칠 때 앱에서도 `toPackQty()` 를 걸고
  "15kg = 1포로 바꿨어요" 를 보여주면 됩니다.
- 규격은 품목 조회에 `pack_unit, kg_per_pack` 을 추가하면 내려옵니다.
- `toPackQty()` 는 웹 전용 import(`@/lib/units`)를 쓰므로 앱에 복사할 때
  `normalizeUnit` 도 같이 옮기거나, 공용 패키지로 빼세요.

## 검증

운영 데이터로 확인할 것:

1. 앱에서 양파 **15** 를 발주 → `order_items` 가 `qty=1, unit='bag'` 인가
2. 그 발주의 단가가 **24,000**(bag 단가)인가. 3,000(kg 단가)이면 2번 버그입니다
3. 양파 **3** 을 발주 → `qty=3, unit='kg'`, 단가 3,000 그대로인가 (배수가 아니므로 변환 없음)
4. 발주 문자에 "양파 1포" 로 나가는가

```sql
-- 변환이 걸렸는지 한눈에
select o.name, b.business_date, p.standard_name, oi.qty, oi.unit, oi.unit_price_snapshot
from order_items oi
join orders ord on ord.id = oi.order_id
join order_batches b on b.id = ord.batch_id
join restaurants r on r.id = b.restaurant_id
join organizations o on o.id = r.organization_id
join products p on p.id = oi.product_id
where p.pack_unit is not null and b.business_date >= current_date
order by b.business_date desc;
```
