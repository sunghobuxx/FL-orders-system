# 핸드오프 — 회원 품목 셀프 추가 (모바일 앱 이식)

작성 2026-08-09 · 웹 구현 완료·배포됨 · 앱은 미착수

## 한 줄

회원이 등록된 전체 품목을 보고 필요한 것을 **직접 자기 발주 목록에 넣는** 기능입니다.
웹(`apps/web`)에는 들어가 있고 운영 배포도 끝났습니다. 같은 것을 회원 앱(`apps/mobile`)에 붙여 주세요.

**서버는 새로 만들 것이 없습니다.** DB 스키마와 API가 이미 있고 앱에서 그대로 부르면 됩니다.
앱에서 할 일은 화면과 호출뿐입니다.

---

## 왜 만들었나

지금은 관리자가 업체별로 발주 가능 품목을 하나하나 등록해 줘야 합니다.
그래서 회원은 자기 목록에 없는 품목을 못 시키고, 전화나 문자로 부탁하게 됩니다.

2026-08-09 실측:

| | 값 |
|---|---|
| 활성 품목 | 137개 |
| 업체별 등록된 품목 | 538건 / 39개 업체 |
| 업체당 평균 | **14개** (최소 1, 최대 37) |

최근 한 달 발주 경로 — 웹 201건 / **어드민이 대신 입력 129건** / 앱 17건.
어드민 대신 입력 129건 중 상당수가 "목록에 그 품목이 없어서"로 보입니다.

---

## 규칙 (이대로 지켜 주세요)

| 항목 | 규칙 |
|---|---|
| 단가 있는 품목 | **즉시** 내 목록에 들어간다 |
| 단가 없는 품목 | 바로 안 열린다. **요청**으로 쌓이고 관리자가 확인 후 승인 |
| 단가 표시 | 오늘 기준 단가를 그대로 보여준다. 실제 청구는 **발주일 기준으로 다시 계산**된다 |
| 삭제 | 회원이 넣은 것(`added_by = 'member'`)만 회원이 뺀다. 관리자가 넣은 기본 품목은 못 뺀다 |
| 새 품목 생성 | 회원은 못 한다. 품목 마스터 등록은 관리자만 |

### 단가 없는 품목을 왜 막나

**단가 없이 발주되면 명세서가 0원으로 나갑니다.** 2026-08-09 에 실제로 있었습니다 —
`일회용 손장갑`이 단가 없이 발주돼 명세서에 0원으로 잡혔습니다.
지금은 관리자가 품목을 등록하면서 단가도 같이 챙기는데, 회원이 직접 넣으면 그 단계가 없어집니다.

단가 없는 품목 23개 중에는 `기타품목`처럼 **애초에 회원이 발주하면 안 되는 것**도 섞여 있습니다.
확인 단계가 그것도 막습니다.

## DB (이미 적용됨 — 손대지 마세요)

마이그레이션 `supabase/migrations/20260811000000_member_product_self_add.sql`

### `restaurant_products` 에 붙은 컬럼

| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `added_by` | text | `'admin'` \| `'member'`, 기본 `'admin'` |
| `added_by_user` | uuid | 넣은 사람 |
| `added_at` | timestamptz | |

기존 538건은 전부 `'admin'` 입니다.

### 새 표 `product_requests`

| 컬럼 | 뜻 |
|---|---|
| `id` | |
| `restaurant_id` | |
| `product_id` | |
| `requested_by` | 요청한 회원 |
| `requested_at` | |
| `status` | `'pending'` \| `'approved'` \| `'rejected'` |
| `decided_at` / `decided_by` | 관리자가 처리한 시각·사람 |

`(restaurant_id, product_id)` 에 **부분 unique** — `status = 'pending'` 일 때만.
처리된 건은 다시 요청할 수 있습니다.

> `restaurant_products` 에 status 를 두지 않고 표를 따로 뺀 이유: 발주 화면이
> `restaurant_products` 를 그대로 읽습니다. 대기 상태를 같은 표에 섞으면 아직 안 열린
> 품목이 발주 목록에 새어 나갑니다.

## ★ RLS — 앱에서 직접 쓰기는 안 됩니다

`apps/mobile/app/(tabs)/order.tsx` 는 지금 `supabase` 세션 클라이언트로
`restaurant_products` 를 **직접 읽고** 있습니다. 읽기는 계속 그렇게 하면 됩니다.

| 표 | 세션 클라이언트로 | 비고 |
|---|---|---|
| `products` | 읽기 O | `products_read` (public) |
| `restaurant_products` | **읽기 O / 쓰기 X** | 쓰기는 `service_role` 만 |
| `product_requests` | **읽기 X / 쓰기 X** | 정책이 하나도 없음 |

그래서:

- 품목 **추가·삭제는 반드시 웹 API** 를 부르세요. 앱에서 `supabase.from('restaurant_products').insert()` 하면 안 됩니다.
- 「담당자 확인 중」 목록도 API 로 받으세요. `product_requests` 는 세션 클라이언트로 조회하면 **빈 배열이 옵니다**.

> Supabase 는 RLS 에 막혀도 **에러를 던지지 않습니다.** `error` 가 null 이고 `data` 만 비어 옵니다.
> "버튼이 안 먹는다"의 단골 원인이니 조용히 실패하는 쪽을 의심해 주세요.

## API (이미 배포됨)

베이스 URL: `MEMBER_API_URL` (`apps/mobile/lib/member-api.ts`) = `https://order.fruitlife.shop`

인증은 **쿠키 세션과 `Authorization: Bearer <access_token>` 둘 다** 받습니다.
앱은 기존 방식 그대로 Bearer 를 쓰세요 — `order.tsx` 의 `/api/member/orders` 호출과 같습니다.

```ts
const { data: { session } } = await supabase.auth.getSession()
headers: { Authorization: `Bearer ${session.access_token}` }
```

### 1. 추가 가능 목록

```
GET /api/member/products?restaurantId=<uuid>&businessDate=YYYY-MM-DD
```

```jsonc
{
  "addable": [
    {
      "id": "2fde2923-...",
      "standard_name": "2리터생수",
      "category": "etc",          // null 일 수 있음 → 'etc' 로 취급
      "default_unit": "bottle",
      "price": 450,               // 단가 없으면 null (0 이 아님)
      "needsApproval": false      // price === null 과 같은 뜻
    }
  ],
  "pending": [
    { "product_id": "0a076b88-...", "standard_name": "고향냉면비빔장" }
  ]
}
```

- 이미 내 목록에 있는 품목, 이미 요청해 둔 품목은 **빠져서** 옵니다
- 이름 가나다순 정렬
- `price` 가 `0` 인 경우는 없습니다. 단가 0 은 "없음"으로 봐서 `null` 로 나갑니다 — **0원으로 표시하면 안 됩니다**
- 실측: 테스트 식당 기준 `addable` 118개 (단가 있음 101 / 없음 17)

| 코드 | 뜻 |
|---|---|
| 401 | 로그인 필요 |
| 403 | 그 식당 권한 없음 |
| 400 | `businessDate` 형식 오류 (`YYYY-MM-DD` 아님) |

### 2. 추가 / 요청

```
POST /api/member/products
{ "restaurantId": "<uuid>", "productIds": ["<uuid>", ...] }
```

```jsonc
{
  "added":     ["2fde2923-..."],   // 바로 열린 것 (단가 있음)
  "requested": ["0a076b88-..."],   // 요청으로 들어간 것 (단가 없음)
  "skipped":   0                   // 이미 목록에 있거나 이미 요청해 둔 개수
}
```

- 단가 유무는 **서버가 판정**합니다. 앱에서 나누지 마세요
- 한 번에 여러 개 보낼 수 있습니다
- `added` / `requested` 는 **실제로 넣은 것만** 들어갑니다. 이미 있는 건 `skipped` 로 셉니다
  (처음엔 이미 있는 것도 `added` 로 돌려줘서 "1개 추가됐습니다"라고 거짓 안내가 떴습니다. `f16f574` 에서 고쳤습니다)

안내 문구는 웹과 같게 맞춰 주세요:

```
2개 추가됐습니다 · 1개는 담당자 확인 중입니다 · 1개는 이미 들어가 있습니다
```

### 3. 빼기

```
DELETE /api/member/products?restaurantId=<uuid>&productId=<uuid>
```

```jsonc
{ "success": true }
```

| 코드 | 본문 | 언제 |
|---|---|---|
| 403 | `담당자가 등록한 기본 품목은 뺄 수 없습니다.` | `added_by = 'admin'` 인 품목 |
| 404 | `목록에 없는 품목입니다.` | 내 목록에 없음 |

**지난 발주 기록은 그대로 남습니다.** 목록에서만 빠집니다. 확인 문구에 그 점을 넣어 주세요.

## 앱에서 할 일

### 1. 발주 화면 — 「+ 품목 추가」 진입점

`apps/mobile/app/(tabs)/order.tsx`

- 품목 목록 아래에 「+ 품목 추가」 버튼 → 품목 고르기 화면으로 이동
- `pending` 이 있으면 그 위에 안내: `담당자 확인 중 · 고향냉면비빔장`
  (`pending` 은 `GET /api/member/products` 응답에서 받습니다)

### 2. 품목 고르기 화면 (새로 만들기)

웹은 `apps/web/app/member/products/add/` 에 **전체 화면 한 장**으로 만들었습니다.
발주 화면 안에 접이식으로 넣었다가 휴대폰에서 목록이 너무 좁아 화면을 통째로 쓰는 쪽으로 바꿨습니다.
앱도 별도 화면으로 가 주세요.

구성:

```
품목 추가                                    [닫기]

[전체 118]  [채소 47]  [양념 21]  [기타 18]  ...   ← 분류 칩, 가로 스크롤

☐ 2리터생수                          450원/bottle
☐ 감자 왕왕                       40,000원/box
☐ 사과                                단가 문의     ← price === null
...

┌────────────────────────────────────────┐
│ 3개 선택   [ 내 발주 목록에 추가 ]        │  ← 화면 하단 고정
└────────────────────────────────────────┘
「단가 문의」 품목은 바로 열리지 않고 담당자 확인을 거칩니다.
```

- 분류는 `CATEGORY_LABELS` 재사용 (`order.tsx` 에 이미 있습니다)
- `category` 가 `null` 이면 `'etc'`(기타)로
- 여러 개 동시 선택
- 추가 후 발주 화면 목록을 다시 불러와야 새 품목이 보입니다

### 3. 발주 화면 — 회원 추가분에 `×`

`loadProducts` 의 select 에 `added_by` 를 더하세요. 지금은:

```ts
.from('restaurant_products')
.select('products(id, standard_name, default_unit, category)')
```

이렇게:

```ts
.from('restaurant_products')
.select('added_by, products(id, standard_name, default_unit, category)')
```

`added_by === 'member'` 인 품목에만 `×` 를 답니다. 누르면 확인 후 DELETE:

```
"2리터생수" 을(를) 내 발주 목록에서 뺄까요?
지난 발주 기록은 그대로 남습니다.
```

관리자가 넣은 품목에는 `×` 를 **아예 그리지 마세요.** 서버도 403 으로 막지만 화면에서 먼저 막는 편이 낫습니다.

### 4. 단가 0원 발주 경고 (같이 넣어 주세요)

회원이 품목을 직접 넣게 되면 0원 발주 위험이 커집니다.
발주를 보내기 전에 단가가 0인 품목이 있으면 경고를 띄웁니다. **막지는 않습니다** —
급해서 일단 시켜야 하는 경우가 있고 관리자가 명세서에서 고칠 수 있습니다.

```
단가가 정해지지 않은 품목이 있습니다 — 사과

그대로 발주하면 금액이 0원으로 잡힙니다. 담당자에게 확인해 주세요.
계속할까요?
```

앱에서는 `unitPrices[product.id]` 가 0이거나 없는 경우입니다
(`loadUnitPrices` 가 `/api/member/product-prices` 로 받아오는 값).

## 검증

**실거래 데이터를 쓰지 마세요.** 테스트 식당으로만 하세요.

```
organization_id  af6378e4-0000-0000-0000-000000000001
restaurant_id    7306bb64-4596-4a5e-92ab-6e9dd9395238
회원 계정         buxxlife82@gmail.com
```

다른 업체의 `restaurant_products` 는 어떤 단계에서도 만들거나 지우지 마세요.
넣어 본 것은 끝나고 지워 주세요:

```sql
delete from restaurant_products
where restaurant_id = '7306bb64-4596-4a5e-92ab-6e9dd9395238' and added_by = 'member';

delete from product_requests
where restaurant_id = '7306bb64-4596-4a5e-92ab-6e9dd9395238';
```

확인할 것 (웹에서는 전부 통과했습니다):

1. 단가 있는 품목 추가 → 즉시 발주 목록에 뜬다
2. 단가 없는 품목 선택 → 요청으로 들어가고 발주 목록에는 **안 뜬다**, 「담당자 확인 중」으로 보인다
3. 관리자가 승인 → 회원 목록에 뜨고 `added_by='member'`
4. 회원 추가분 빼기 → 목록에서 사라진다
5. 관리자가 넣은 기본 품목 → `×` 가 없고, API 로 직접 불러도 403
6. 단가 0 품목 발주 → 경고가 뜬다
7. 같은 품목 두 번 요청 → 목록에 안 보이고, 직접 보내도 `skipped` 로 처리된다
8. 다른 업체 `restaurantId` 로 호출 → 403

## 주의사항

- **DB 는 이미 적용돼 있습니다.** 마이그레이션을 다시 돌리지 마세요.
- **웹 API 는 배포 완료입니다.** 앱에서 바로 부를 수 있습니다 (2026-08-09 확인: 무인증 GET → 401 응답).
- 운영 DB 는 하나뿐입니다. 로컬 개발도 같은 DB(`nvpaggacvbotgqyxfdof`)를 봅니다. 시험 데이터가 그대로 운영 데이터입니다.
- 앱 배포는 웹이 먼저 나간 뒤에 하면 됩니다. 이미 나갔습니다.

## 이 핸드오프에서 다루지 않는 것

- 관리자 승인 화면 — 웹에만 있으면 됩니다 (`/admin/products/requests`)
- 요청 알림(문자·푸시) — 만들지 않았습니다. 관리자가 화면을 봐야 압니다
- 품목 검색 — 137개라 분류별 목록으로 충분하다고 봤습니다. 더 늘면 그때
- 회원이 새 품목을 만드는 것 — 관리자만
