# 정산 확정 · 잠금 · 통지

작성일 2026-08-09

## 배경

거래처에 넘긴 정산 금액이 나중에 바뀐다. 시스템이 계산한 값이 매주 달라지는 것처럼
보이면 거래처가 숫자를 믿지 못한다. 이것이 이 작업의 유일한 이유다.

### 실제로 벌어진 일 — 할매 천호점 435,700

```
07-13 01:50  7/13 발주 정상 접수
07-18 13:00  7/13~7/19 정산서 생성  →  7/13 명세서가 아직 없어 청구액 423,700
07-23 02:33  입금 606,500 기록      →  423,700 기준으로 수금
07-23 15:26  7/13 명세서 211,900 뒤늦게 생성  →  청구액 635,600 으로 상승
```

수금이 끝난 뒤 청구액이 올라가 차액이 남았다. 입금은 오래된 미수금부터 자동 배분되므로
그 차액은 매주 다음 기간으로 밀렸고, 3주 동안 435,700 이 그대로 굴러다녔다.
2026-08-09 에 재수금 불가로 판단해 0 처리했다.

### 규모

명세서 생성 지연 (2026-06-01 이후):

| 구분 | 건수 | 금액 |
|---|---|---|
| 당일 이전 생성(정상) | 751 | 79,832,084 |
| 1일 지연 | 19 | 1,994,350 |
| 2~6일 지연 | 24 | 2,450,630 |
| 7일 이상 지연 | 5 | 576,250 |

지연 48건의 생성 시각이 한 시점에 뭉쳐 있다(`07-29 22:04` 에 영업일 7/07·7/11·7/24·7/25
7건 생성 등). 자동 생성이면 나올 수 없는 분포다. 밀린 명세서를 사람이 몰아서 만든 흔적이다.
발주 자체는 제때 접수됐고, 경로별로는 40건이 웹 API 다 — 모바일 앱이 주범이 아니다.

2026-08-08 배포한 `spec-sweep-hourly` 로 지연은 최대 1시간으로 줄었다.
그러나 정산서가 매일 04:00 에 만들어지므로 그 사이에 어긋나면 같은 일이 다시 난다.

## 목표

거래처에 넘긴 정산서 금액은 그 뒤로 바뀌지 않는다.

## 하지 않는 것

- **모바일 푸시** — `push_token` 보유 0/45. 지금 붙여도 도달이 0이라 검증이 안 된다.
  채널 선택 구조만 열어 두고 별도 건으로 다룬다.
- **전체 일괄 확정** — 선택 확정으로 시작해 안정화 후 전환한다.
- **소액 잔액 문제** — 청구액보다 입금이 조금 적어 남는 몇천원(2026-08-09 에 5건
  21,590 정리). 원인이 사후 변경이 아니라 별개다.
- **확정 해제** — 아래 「확정 해제를 만들지 않는 이유」 참고.

## 확정의 정의

「확정」은 세 가지를 한 번에 한다.

1. **잠금** — 그 정산서 금액을 더 이상 바꾸지 못하게 한다
2. **기록** — 누가 언제 확정했는지, 그때 금액이 얼마였는지 남긴다
3. **발송** — 거래처에 청구 내용을 보낸다

1이 핵심이고 3은 부수다. **발송이 실패해도 확정은 유지한다.** 확정을 되돌리면 이미 넘긴
금액이 또 바뀔 수 있다. 발송 실패는 따로 표시하고 재발송으로 처리한다.

## 데이터 모델

`sales_statements` 에 추가:

| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `confirmed_at` | timestamptz | 확정 시각. null 이면 미확정 |
| `confirmed_by` | uuid | 확정한 사람 |
| `confirmed_total` | numeric | 확정 당시 청구액 |
| `notified_at` | timestamptz | 발송 성공 시각. null 이면 미발송 |

`confirmed_total` 을 따로 두는 이유: 어떤 경로로든 금액이 바뀌었을 때 「넘긴 금액과 지금
금액이 다르다」를 즉시 잡기 위해서다. 천호점 건이 이 대조가 없어 3주를 굴러다녔다.

공개 링크용 신규 테이블 `statement_share_links`:

| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `token` | text (PK) | 추측 불가능한 무작위 문자열 |
| `statement_id` | uuid | 대상 정산서 |
| `expires_at` | timestamptz | 발급 시점 + 7일 |
| `created_at` | timestamptz | |

기존 `settlement_periods.status`(open/closed)는 기간 전체 단위라 업체별 확정에 쓸 수 없다.

## 잠금은 두 모듈에만 건다

정산서 금액을 건드리는 코드는 10곳이지만, 실제로 금액을 쓰는 함수는 둘뿐이다.

```
lib/settlement/generate.ts     generateStatements()    04:00 크론, 명세서 동기화
lib/settlement-finance.ts      syncStatementFinance()  나머지 9곳이 전부 경유
```

이 두 함수 입구에서 `confirmed_at` 이 있으면 그 정산서를 건너뛴다. 라우트마다 검사를
흩어 놓으면 새 라우트가 생길 때 또 뚫린다.

`syncStatementFinance` 를 경유하는 9곳 (라우트 8 + 서버액션 1):
`admin/products/actions.ts`, `api/admin/products/price-snapshots`,
`api/admin/products/org-prices`, `api/admin/settlement/periods/[id]/calculate`,
`api/admin/settlement/update-spec-line`, `api/admin/settlement/recalculate-spec`,
`api/admin/orders/items`, `api/admin/orders/update-items`, `api/driver/orders/items`

기존 `skipSettled`(완납 건너뛰기)와는 다르다. 완납은 「돈을 다 받았다」이고 확정은
「금액을 넘겼다」다. 부분수금 상태에서도 잠겨야 한다 — 천호점이 그 틈으로 샜다.

## 확정 후 늦게 온 명세서

잠긴 정산서에 명세서가 뒤늦게 붙으려 하면 **다음 정산 기간으로 넘긴다.**

```
8/03 명세서가 8/10 에 생성됨
  → 8/02~8/08 정산서는 확정됨(잠김)
  → 8/09~8/15 정산서에 「8/03 지연분」으로 붙는다
```

명세서 자체는 그대로 둔다. 실제 납품 기록이므로 날짜를 바꾸면 안 된다. **정산서에 담기는
위치만** 다음 기간으로 간다. 회원 화면에도 「전주 지연분」으로 표시해 이번 주 청구에
지난주 날짜가 있는 이유를 알 수 있게 한다.

구체적으로 `generateStatements` 가 한 기간의 명세서를 모을 때, 그 명세서가 속한 기간의
정산서가 이미 확정됐으면 그 명세서를 **현재 만드는 정산서에 포함시킨다.** 즉 명세서를
기간으로 가르는 기준이 「명세서의 business_date」 하나에서 「business_date + 그 기간
정산서의 확정 여부」 둘로 바뀐다. 한 번 다음 기간에 담긴 명세서는 그 기간 정산서가
확정되면 거기에 고정된다.

이렇게 하면 넘긴 청구서는 안 바뀌고, 빠진 돈도 사라지지 않는다.

## 확정 해제를 만들지 않는 이유

해제를 열어 두면 「확정했는데 또 바뀐다」가 가능해져 목적이 무너진다.
잘못 확정했으면 그 정산서는 그대로 두고 **차액을 다음 기간에 조정 라인으로 넣는다.**
실수를 되돌리는 길은 열되 이미 넘긴 종이는 건드리지 않는다.

## 금액 어긋남 감지

`confirmed_total` 과 현재 `total_amount` 가 다르면 어드민 정산 화면에 경고를 띄운다.

```
⚠ 넘긴 금액 721,000 / 현재 금액 932,900 — 211,900 차이
```

잠금이 뚫리는 경로가 남아 있어도 조용히 지나가지 않고 드러난다.

## 확정 화면

`/admin/settlement` 에 「정산 확정」을 둔다. **마감된 기간**(기간 종료일 < 오늘 KST)만 보인다.
진행 중인 기간은 아직 금액이 늘어날 수 있으므로 확정 대상이 아니다.

```
정산 확정 — 2026-08-02 ~ 08-08                 [선택한 3곳 확정·발송]

☑ 할매 천호점      646,800   이전 0        합계 646,800    010-****-1234
☑ 할매 고강점      795,020   이전 0        합계 795,020    010-****-5678
☐ 컨셉트원         769,500   이전 0        합계 769,500    ⚠ 연락처 없음
☐ 아구 강남      1,169,500   이전 504,500  합계 1,674,000  ⚠ 연락처 없음
```

금액을 훑고 체크해 확정한다. 발송은 되돌릴 수 없으므로 한 번은 눈으로 보고 넘어간다.
안정화 후 「전체 확정」으로 전환한다.

연락처 없는 5곳(알찬식자재·와이로지스·아구 공덕·아구 강남·컨셉트원)은 경고를 달고,
확정은 되지만 발송은 실패로 남긴다. 조용히 안 가는 것이 가장 위험하다.

## 발송

### 채널 선택

한 함수에서 정한다. 나중에 우선순위만 바꾸면 된다.

```
푸시 토큰 있음  → 앱 푸시        ← 이번 범위에서는 만들지 않는다. 분기 자리만 비워 둔다
알림톡 가능     → 알림톡 + 「정산서 보기」 버튼
그 외          → 문자
연락처 없음     → 발송 실패로 기록
```

푸시 분기는 이번에 구현하지 않는다. 채널 선택 함수의 형태만 이렇게 잡아 두어, 3단계에서
분기 하나를 채우면 되게 한다.

`lib/messaging/kakao.ts` 의 `sendKakaoAlimtalk` 은 템플릿이 없거나 발송이 실패하면
`sendSms` 로 자동 폴백한다. 따라서 **알림톡 기준으로 짜 두면 템플릿 승인 전에는 문자로
나가다가, 승인되는 날 템플릿 ID만 넣으면 알림톡으로 바뀐다.** 코드를 두 번 짜지 않는다.

정산용 알림톡 템플릿은 새로 승인받아야 한다(기존 `SOLAPI_DISPATCH_TEMPLATE_ID` 는
발주용). 승인은 보통 영업일 2~3일. 환경변수 `SOLAPI_SETTLEMENT_TEMPLATE_ID` 로 분리한다.

### 내용

```
[FruitLife] 정산 안내

할매솥뚜껑삼겹살 천호점
2026.08.02 ~ 08.08

당기 청구   646,800원
이전 미수금       0원
─────────────────
총 청구액   646,800원

정산서 보기 ▸ https://order.fruitlife.shop/s/<token>
```

알림톡이든 문자든 **링크는 동일하게 들어간다.** 알림톡에서는 버튼으로, 문자에서는 본문
마지막 줄로 나간다. 폴백으로 문자가 나가도 거래처가 정산서를 볼 수 있어야 한다.

### 발송 실패

확정과 분리한다. 발송이 실패해도 `confirmed_at` 은 남고 `notified_at` 만 비어 있다.
화면에 「확정됨 · 발송 실패」로 표시하고 재발송 버튼을 둔다.
발송 이력은 누구에게 언제 무엇이 갔는지 남긴다.

## 공개 정산서 링크

`/s/<token>` — 로그인 없이 그 정산서 한 장만 보인다.

- 토큰은 추측 불가능한 무작위 문자열
- **유효기간 7일**. 지나면 「기간이 지난 링크입니다」와 함께 로그인 안내
- 확정 시 발급하고, 재발송 시 남은 기간이 있으면 재사용한다

명세서 내역이 담기므로 주소가 새면 남이 볼 수 있다. 유효기간이 그 노출 범위를 제한한다.

## 기존 데이터

과거 정산서는 건드리지 않는다. `confirmed_at` 이 비어 있으면 지금까지처럼 동작한다.

다만 **완납된 과거 정산서는 확정된 것으로 채운다.** 이미 받은 돈이라 금액이 바뀌면 안 된다.

```
receivables.status = 'paid' 인 정산서
  → confirmed_at    = 그 정산서의 마지막 입금 시각
  → confirmed_total = 현재 total_amount
```

## 검증

운영 반영 전에 확인한다. 1~3이 핵심이다 — 잠금이 두 모듈에만 걸려 있으므로 세 경로가
막히면 나머지도 막힌다.

1. 잠긴 정산서에 명세서를 붙인다 → 금액이 안 바뀌고 다음 기간으로 넘어가는가
2. 잠긴 정산서에 단가를 재적용한다 → `price-snapshots` 경로가 막히는가
3. 명세서 라인을 직접 수정한다 → `update-spec-line` 경로가 막히는가
4. 확정 → 실제 번호 1건에 도달하는가
5. 연락처 없는 업체를 확정한다 → 확정되고 발송 실패로 남는가
6. 공개 링크를 연다 → 로그인 없이 보이는가, 7일 뒤 막히는가
7. `confirmed_total` 과 현재 금액이 다를 때 경고가 뜨는가

검증은 운영에 실제 브라우저로 붙어서 한다. 서버 액션·엣지 런타임 문제는 로컬에서
드러나지 않는다.

## 일정

```
1단계  확정·잠금 + 발송(문자로 나감)      ← 금액이 안 바뀌는 것부터
2단계  알림톡 템플릿 승인 후 ID 만 교체    ← 코드 변경 없음
3단계  앱 푸시로 전환                     ← 토큰 문제 해결 후, 별도 건
```

금액이 안 바뀌게 하는 것이 급하고 채널은 그다음이다. 폴백 덕분에 채널 전환에 코드 변경이
없다.

## 열린 문제

- **푸시 토큰 0건의 원인** — 앱 설치자가 없는 것인지 토큰 저장이 깨진 것인지 미확인.
  3단계 전에 규명 필요.
- **소액 잔액** — 입금이 청구보다 조금 적게 기록되는 이유가 거래처의 실제 부족 입금인지
  기록 누락인지 미확인. 별도 건.
