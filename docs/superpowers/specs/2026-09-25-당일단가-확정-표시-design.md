# 당일 단가 확정 표시 — 설계

- 작성: 2026-09-25 / 상태: **사장님 검토 대기**
- 범위: 웹 업체 화면 + 어드민 + 서버 API(업체용·배송앱용) + 웹 인쇄 화면. **회원앱·배송앱 화면은 코덱스 핸드오프 문서(2개)만 작성한다.**

## 1. 배경과 문제

사장님이 품목마스터에 단가를 넣는 시각과, 업체가 명세서를 확인하는 시각이 다르다.
업체가 본 금액이 나중에 단가 입력으로 바뀌어서 **입금을 못 하거나 "금액이 바뀌었다"는 혼란**이 생긴다.

실제 입력 기록: 2026-09-24 단가는 12:41 ~ 13:07 사이에 품목별로 나뉘어 들어갔고,
그 사이에 값이 바뀐 것도 있다(깻잎 51,000 → 32,000, 청오이 1,000 → 1,500).
단가를 넣는 화면은 품목별 `PriceSnapshotForm` 한 곳뿐이라 하루치가 한 번에 들어오지 않는다.

## 2. 목표와 성공 기준

업체가 **명세서만 보고 "지금 금액이 확정인지, 바뀔 수 있는지"** 알 수 있다.

## 3. 사장님과 정한 것

| 질문 | 결정 |
|---|---|
| "오늘 단가가 들어왔다"를 무엇으로 판단하나 | **확정 버튼** — 사장님이 「오늘 단가 확정」을 눌러야 확정 (자동 판단은 입력 도중에 "당일"로 오판) |
| 확정 뒤에 단가를 고치면 | **확정이 자동으로 풀린다** — 「단가 수정됨」으로 바뀌고 다시 확정해야 한다 |
| 확정을 깜빡하면 | 그대로 두고 **어드민 대시보드에 경고**. 업체 화면의 「입력 중」은 정산서 확정 시 사라진다 |
| 범위 | 웹 업체 화면 + 어드민 + 서버 API + 웹 인쇄 화면. 앱 표시는 핸드오프 |
| 배송앱 | 아침 배송 매니저는 **전날 명세서**를 날짜를 골라 인쇄한다. 확정 전 날짜는 인쇄하지 않고 확정된 전날 것을 뽑는다. → 인쇄 전 **경고창·차단 없이 표시만** 한다(목록 배지 + 인쇄물 문구) |

## 4. 설계

### 4.1 데이터 (마이그레이션 1개)

- **표 `price_confirmations`**: `business_date date primary key`, `confirmed_at timestamptz not null`,
  `confirmed_by uuid`. 다시 확정하면 같은 행의 `confirmed_at` 을 갱신한다.
- **뷰 `price_day_last_change`**: `select effective_from as business_date, max(created_at) as last_price_at
  from price_snapshots group by effective_from`. 날짜 수만큼(최대 약 31행)만 읽으므로
  PostgREST 1,000행 제한에 걸리지 않는다.
- RLS: 표는 켜고 정책을 만들지 않는다. 읽기·쓰기는 **서버의 service role 로만** 한다
  (날짜별 확정 여부만 나가므로 노출 위험은 없고, 회원 RLS 를 새로 열지 않는다).
- 상태는 **저장하지 않고 열 때 계산**한다. 단가를 쓰는 경로가 몇 개든(어드민 화면, 제가 DB로 직접 고치는 경우)
  `created_at` 은 DB가 채우므로 자동으로 "수정됨"이 감지된다.

### 4.2 상태 계산 — 순수 함수 `priceStatus` (`lib/pricing/price-status.ts`)

입력: 날짜 D, 시행일 `PRICE_STATUS_FROM`, 확정 시각, **적용일이 D 이하인 단가 중 확정 뒤에 등록된 것의 마지막 등록 시각**,
그 날짜를 포함한 정산서가 확정됐는지. **오늘 날짜나 화면 종류는 보지 않는다** — 순수하게 상태만 돌려준다.

| 순서 | 조건 | 상태 |
|---|---|---|
| 1 | D < `PRICE_STATUS_FROM` (시행일 이전) | `none` |
| 2 | 그 날짜를 포함한 정산서가 확정됨 | `final` (확정 정산서 금액이 최종) |
| 3 | 확정 기록 있음 + `last_price_at > confirmed_at` | `modified` (수정 시각 = `last_price_at`) |
| 4 | 확정 기록 있음 | `confirmed` (확정 시각) |
| 5 | 확정 기록 없음 | `pending` |

**화면마다 보여주는 범위는 다르다** (`displayFor(audience, status, D, 오늘)`):

| 상태 | 업체 화면 (member) | 배송앱·배송앱 인쇄물 (driver) |
|---|---|---|
| `none` | 표시 없음 | 표시 없음 |
| `final` | 표시 없음 | 「정산 확정」 (작게) |
| `confirmed` | 당일명세서에만 ✓ (정산서 화면은 생략) | ✓ 당일 단가 확정 |
| `modified` | 나이와 관계없이 표시 | 나이와 관계없이 표시 |
| `pending` | **오늘·어제 날짜만** 표시 | **나이와 관계없이 항상 표시** |

- 업체 화면에서 오래된 `pending` 을 숨기는 이유: 사장님이 놓친 날짜에 "입력 중"이 몇 주씩 남는 것을 막기 위해서다
  (대신 대시보드가 알려준다).
- **배송앱은 숨기지 않는다:** 전날 명세서를 골라 인쇄하는데, 오래된 미확정 날짜에 표시가 없으면
  "확정이라 표시가 없는 것"으로 오해하기 때문이다. 배송앱에서는 표시가 없는 날짜는 시행일 이전(`none`)뿐이다.
- **"수정됨" 은 그 날짜 단가만 보지 않는다.** 단가 등록은 `effective_from` **이후의 모든 날짜** 명세서를 덮어쓰므로
  (`/api/admin/products/price-snapshots`), 어제 날짜로 단가를 넣으면 오늘 명세서 금액도 바뀐다 — 사장님이 실제로 하시는 방식이다
  (2026-09-24 에 9/23 단가 12건을 입력). 그래서 D 는 **확정 뒤에 등록된 `effective_from ≤ D` 단가가 하나라도 있으면** 수정됨이다.
  내일 날짜(`effective_from > D`) 단가는 D 에 영향이 없다. (검토에서 발견해 2026-09-25 고쳤다.)
- 업체별 고정단가(`org_product_prices`)와 명세서 한 줄 수동 수정은 특정 업체 한 곳만 바뀌는 것이라 감지 대상이 아니다(범위 밖).
- `PRICE_STATUS_FROM` 은 **배포 당일(KST)** 로 정한다. 시행일 이전 날짜에 표시를 안 하는 이유는,
  월정산 업체(마산 등)의 9월 초 날짜가 전부 "입력 중"으로 뜨는 것을 막기 위해서다.
- 로더 `loadPriceDayStatuses(adminDb, dates)`: `price_confirmations` 와 `price_day_last_change` 를
  날짜 목록으로 조회하고, 정산서 확정 여부를 합쳐 `priceStatus` 에 넘긴다. 날짜 수만큼만 읽는다.

### 4.3 어드민

- **품목마스터(`/admin/products`) 상단 바**: `오늘 단가: 입력 중 | 확정 13:10 | 수정됨` 과
  **[오늘 단가 확정]** 버튼. 날짜 선택 기본값은 오늘이고, 지난 날짜(예: 어제 단가를 오늘 고친 경우)도 확정할 수 있다.
  미래 날짜는 확정할 수 없다(오늘까지).
- **API `POST /api/admin/price-confirmations` `{ date }`**: `getAdminSession()` 으로 관리자만 허용,
  날짜 검증, `price_confirmations` upsert(`confirmed_at = now()`, `confirmed_by`). 확정 취소는 만들지 않는다
  (잘못 눌러도 단가를 하나 새로 등록하면 "수정됨"이 되고, 다시 확정하면 된다).
- **대시보드 경고**: 오늘 단가 미확정(입력 중), 확정 뒤 수정됨, 어제 이전 미확정 날짜 수.

### 4.4 업체 화면 (웹)

- **당일명세서(`/member/spec`)**: 선택한 날짜의 배지. 문구는 4.6.
- **정산서(`/member/settlement`)**: 정산서 기간 안에 "입력 중" 또는 "수정됨" 날짜가 있으면 상단에 안내 한 줄
  (예: "9/24 명세서는 단가 입력 중입니다"). **"확정" 표시는 붙이지 않는다**(월정산 목록이 ✓로 도배되는 것을 피함).
- **문자 공유 링크(`/s/[token]`)**: 변경 없음. 링크는 정산서 **확정 시점에만** 발급되므로(`settlement/confirm`,
  `payment-request`) 표시 대상이 아니다.
- **웹 인쇄 화면**(`/member/spec/print`, `/print/spec`): 인쇄된 종이 맨 위에 상태 문구를 찍는다
  (`pending`·`modified`·`confirmed` 일 때. `final`·`none` 은 찍지 않는다). 종이로 나간 금액이 임시인지
  확정인지 받는 사람이 알 수 있게 하기 위해서다.
- `member/` 화면은 과거 복원 사고가 있어서 **기존 로직은 건드리지 않고 표시만 더한다.**

### 4.5 서버 API

- `GET /api/member/settlement` 응답에 `priceStatuses: [{ date, status, at }]` 를 더한다
  (`status`: `pending` | `confirmed` | `modified`. 업체 표시 범위 밖인 날짜는 목록에서 뺀다).
- `GET /api/driver/specs` 응답의 각 명세서에 `priceStatus: { status, at }` 를 더한다
  (`status`: `pending` | `confirmed` | `modified` | `final`, 시행일 이전은 필드 없음). 배송앱 표시 범위(위 표)를 따른다.
  `mode=history` 목록에도 같은 필드가 붙는다.
- 두 API 모두 기존 필드는 그대로라서 **앱이 업데이트되기 전에도 앱은 지금처럼 동작한다.**

### 4.6 문구 (한 곳에서 관리 — `priceStatusText`)

| 상태 | 문구 |
|---|---|
| 입력 중 | 단가 입력 중 · 금액이 바뀔 수 있습니다 (이전 단가 기준) |
| 확정 | ✓ 당일 단가 확정 (13:10) |
| 수정됨 | 단가 수정됨 · 금액이 바뀔 수 있습니다 (13:40 수정) |

### 4.7 배송앱 (핸드오프)

배송앱은 「명세서」 탭에서 `/api/driver/specs` 로 명세서를 받고, **앱 안에서 인쇄용 화면(`createSpecHtml`)을 만들어**
`expo-print` 로 바로 인쇄한다. 아침 배송 매니저는 날짜 선택(`DateSelector`)으로 **전날 명세서**를 골라 뽑는다.

- **목록:** 명세서 카드에 상태 배지(위 4.6 문구). 확정 전 날짜는 눈에 띄는 색으로 보여서 "이건 뽑지 않는다"를 알 수 있게 한다.
- **인쇄물:** `createSpecHtml` 맨 위에 같은 상태 문구를 찍는다(`final`·없음은 찍지 않는다).
- **경고창·차단은 만들지 않는다.** 매니저가 배지를 보고 스스로 고르는 흐름이고, 차단하면 사장님이 확정을 늦게 하는 날
  명세서를 못 뽑는다.
- 인쇄 HTML 이 앱 안에 있어서 **앱이 업데이트되기 전에는 종이에 표시가 찍히지 않는다.** 웹 인쇄 화면은 서버 배포 즉시 적용된다.
- 핸드오프 문서 2개: `docs/handoff/codex/2026-09-25-앱-단가확정-표시-회원앱.md`,
  `docs/handoff/codex/2026-09-25-앱-단가확정-표시-배송앱.md` (API 필드 명세, 문구, 표시 규칙, 인쇄 문구 위치).

## 5. 엣지와 알려진 한계

- **감지하지 못하는 것:** ① 명세서 한 줄을 손으로 고친 경우 ② 업체별 고정단가 변경 ③ `price_snapshots` 행 삭제
  (공급처 삭제 경로). 모두 특정 업체 한 곳에 한정되거나 드문 경로라 이번 범위에서 뺀다.
- **시각 비교:** 확정 시각과 단가 등록 시각은 둘 다 DB 시계(`now()`)라 서버 시계 차이가 없다.
- 확정 기록 없이 오래된 날짜는 업체 화면에 표시하지 않는다. 사장님이 놓친 날짜는 대시보드가 알려준다.
- 동시에 두 명이 확정해도 upsert 라 결과는 같다.

## 6. 테스트

- `priceStatus` 표 기반 테스트: 위 5개 규칙의 모든 분기, 경계(시행일 당일, `last_price_at == confirmed_at`).
- `displayFor` 표 기반 테스트: 업체/배송 표시 범위(오늘·어제 경계, 오래된 `pending` 은 업체에서 숨김·배송에서 표시).
- `POST /api/admin/price-confirmations`: 비관리자 403, 잘못된 날짜 400, 미래 날짜 400, 정상 upsert, 재확정 시 시각 갱신.
- `GET /api/member/settlement`: `priceStatuses` 포함, 기존 필드 불변.
- `GET /api/driver/specs`: 각 명세서에 `priceStatus` 포함(`history` 포함), 기존 필드 불변.
- 로더: 날짜 수만큼만 조회(행 제한 회피), 정산서 확정 날짜는 제외.
- 화면은 타입체크와 렌더 확인(로컬 dev 서버)으로 검증한다.

## 7. 범위 밖

업체 알림(푸시·문자), 확정 취소 버튼, 명세서 한 줄 수동 수정·업체별 고정단가 감지, 앱 화면 구현(회원앱·배송앱), 배송앱 인쇄 전 경고창·차단.

## 8. 구현 시 정할 것

- `PRICE_STATUS_FROM` 값(배포 당일).
- 품목마스터 상단 바의 정확한 배치와 대시보드 경고 카드 위치.
- 웹 인쇄 화면 두 곳(`/member/spec/print`, `/print/spec`)의 실제 사용처 확인 후 문구 위치 확정.
